# A connection carries no identity, so "Presenter" is an intention rather than a check

There is no login, no role, and no token on a WebSocket connection (ADR-0002). Any phone on the hotspot that reaches `/ws` is, to the server, indistinguishable from the Backbone. `startShow` is therefore accepted from any connected socket, and a Player phone that sent `{"kind":"startShow"}` by hand would close the join window for the whole room.

The rejected option is a Presenter token: the server generates one at startup, prints it, and hands it to the Backbone, which attaches it to `startShow`. It was rejected because it does not buy what it appears to buy. The Backbone's browser fetches the token from the same open HTTP server that serves the Player page, so a phone can read the token as easily as the Presenter can — it raises the effort from "open a console and type JSON" to "open a console, type JSON, and fetch a URL", while adding a protocol change, a route, and a place for the token to leak. Real identity here would need something the phone does not have, which for a classroom presentation means a physical act by the Presenter rather than a secret.

What is enforced instead: a socket that has *asked* to be a Player — and was let in or turned away — can never drive the show. That is a real invariant, it costs nothing, and it closes the specific case where a Player's own phone does it. A socket that has asked for nothing at all is still treated as the Presenter's. The three controls behind "drives the show" are `startShow`, `presentQuestion`, and `reveal`.

This was sharpened after ticket 02. It originally read "claimed a place on the roster", which is a different and weaker question: `planJoin` refuses a phone without a claim, so a phone turned away after the show started held no claim, was indistinguishable from the Backbone, and inherited all three controls. It could put up a question no one asked for and publish an answer nobody had answered yet. Asking is the right test, not claiming — a refusal is as much a statement of intent as a place on the roster.

This is accepted deliberately, for a room of classmates playing a ten-minute segment with no adversary; the cost of the token is permanent complexity in the protocol. Revisit if the show ever leaves a classroom.

The cost if it is ever wrong changed with ticket 02, and the old wording understated it. "A show that starts thirty seconds early, which is recoverable by restarting" was true when `startShow` was the only control on this gate. Now all three are behind it, so the worst case is a phone calling `reveal` and the correct answer going up on the Stage in front of the room before anyone has answered. That is not recoverable by restarting: the reveal has already been seen, and the question is burned for everyone in the room. Ticket 02's Backbone countdown is what bounds it — there is only a window of seconds between a question going up and the answer being publishable — but the window is the whole of it, and a player who knows the room has a phone can fire inside it.
